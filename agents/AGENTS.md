## 工作方式

- 当前用户要求和当前路径下更具体的项目指令优先于个人全局默认；发生冲突时按更具体的要求执行并显式说明关键影响。
- 默认直接开始工作；命令实际失败后再检查环境，环境检查围绕已出现的错误展开。
- 当因缺少工具阻塞当前任务时，自行安装所需的工具；在受信任的 Unix 或 WSL 环境中可直接使用免密 `sudo`，其他平台使用对应的包管理方式。Windows 平台需要将所需工具安装在 D 盘的合理路径下。
- 文档、注释和面向用户的说明默认使用中文；用户要求、项目既有规范或外部格式另有规定时，以更具体的要求为准。
- 下载文件时优先使用多线程下载工具`aria2c`。

## 执行规则

1. 上层不可引用下层细节，避免下层细节更新时，上层也会更新。
2. 通过组合模块的的方式进行管理，大模块包含小模块，每个模块是完整的项目单元，下层模块通过引用上层环境实现可迁移的命令。
3. 上层不校验下层输出，由最小的模块单元自行处理校验，上层以下层的输出结果合集判断任务是否成功。
4. 文档编写时提供下层模块的简单描述，保证文档的稳定性，除非下层模块增加或减少或是重大功能变更，不要轻易更新上层文档。违反此规则的现有文档可以完全重写。
5. 目录组织使用单向图依赖，具有层次划分。违反此规则的现有目录组织可以完全重构。
6. 降低校验的复杂度，总是让该功能直接依赖的模块进行校验。如果一个变更导致了多个文档的修改，多条校验条件的更新，那么这条设计是不合理的。

## 删除规则

- 在 PowerShell 中使用 `Remove-Item` 的默认参数和确认行为删除文件或目录；
- 在 Unix 中使用 `rm` 的默认参数删除文件或目录；

## 测试规则

**默认使用一次性测试完成验收，并在验收结束后移除；用户明确要求长期测试时再建立长期测试。**

在建立任何测试时，使用如下规则实现：

- 测试以用户可观察行为为对象，保持实现细节独立；
- 失败时快速终止


## 文档编写规则

* 最终文档只描述目标环境当前支持的用法。
* 使用目标环境原生术语，优先写正向、可执行的规则。
* 不保留旧系统名称、旧 API、旧命令、旧角色或废弃术语。
* 不通过“不要使用旧系统的 X/Y/Z”来定义目标行为；应改写为“使用 A 完成 B”。
* 如果旧概念在目标环境中不存在，默认直接省略，不需要说明其不存在。
* 最终规则应保持最小充分：目标规则已经能完整约束行为时，不再添加旧环境的反向禁止列表。

除非用户明确要求兼容性说明、新旧对比、Breaking Changes 或 Changelog，否则不要在最终产物中保留旧系统信息。

输出前检查：

> 最终文档应描述“现在应该怎么做”，而不是“以前不要怎么做”。
