# 提交工作区

## Workflow

1. 读取当前路径适用的 `AGENTS.md`、仓库说明和验证入口，确认提交范围与质量门；如果上下文已经明确给出这些信息，只补充读取缺失部分。
2. 使用非交互 Git 命令检查工作区。优先运行 `git status --short`、`git diff --stat`，并按需读取具体差异。
3. 区分当前任务修改、用户已有修改和无关修改；提交范围默认限定为当前任务相关内容，用户明确要求提交整个工作区时扩展到全部修改。
4. 根据上下文判断当前差异是否已有充分验证证据。如果上下文明确表明当前修改内容已经通过相关测试、lint、构建或检查，且验证后没有再发生改动，则跳过重复验证；否则从仓库约定中发现并运行与改动相关的验证命令。验证失败时保留显式失败状态；只有用户明确要求时才创建带失败状态的提交。
5. 根据差异意图和路径确定具体子系统，再通过 `git log --oneline -n 10 -- <path>` 或等价命令校准近期 scope 命名。
6. 暂存提交所需的已跟踪和未跟踪文件，不改动无关文件的暂存状态；按 `type(scope): message` 生成提交信息，执行普通的 `git commit -m`。
7. 报告验证命令及结果；若根据上下文跳过重复验证，说明采用的已有验证证据；同时报告提交信息、提交哈希、当前分支和提交后的工作区状态。

## 提交信息

根据改动意图选择 `type`：

- `feat`：新增用户可见能力
- `fix`：修复缺陷或纠正行为
- `docs`：仅修改文档
- `refactor`：保持预期行为的内部重构
- `test`：新增或更新测试
- `build`：构建、依赖或打包修改
- `ci`：持续集成修改
- `chore`：不属于以上类型的日常维护

选择简短英文 `scope`，表达差异对应的具体行为或子系统。按以下顺序判断：

1. 优先使用差异所表达的用户行为或运行域，目录名作为辅助线索。
2. 优先复用近期历史中具体且语义一致的 scope。
3. 多个文件共同支持同一行为时，使用该行为作为 scope。
4. 多个子系统确实同时变化时，使用主要交付行为；无法证明更具体范围时才使用 `repo`。

`message` 默认使用简洁中文，聚焦主要结果。例如：

- `docs(build): 新增本地构建说明文档`
- `fix(login): 修复短信验证码重复发送问题`
- `refactor(network): 整理请求错误处理逻辑`
- `fix(flash): 修复 A/B 分区 USB 烧录链`

## 边界

- scope 依据差异表达的行为确定，文件名只作为路径线索。
- 工作区没有可提交修改时明确说明并保持现有状态。
- 无关修改已经暂存时，保持其暂存状态；优先使用安全的路径限定提交，无法隔离时停止并说明边界。
- 使用非交互 Git 命令。
- 提交、推送、amend、force-push、rebase 或其他历史改写操作均等待用户明确要求。
